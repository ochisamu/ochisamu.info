今週は、AI エージェント系の「見えているものと実際に読んでいるものが違う」話が2本並んでいて、どちらも運用目線で気になりました。片方は WebFetch の中身、もう片方は Codex の使い分けです。実装してみる前に挙動を疑っておくと事故りにくい、という内容でした。

## Claude Code の WebFetch は全文読解ではないことがある

**元記事**  
[あなたのClaude CodeのWebFetch、実はWebをちゃんと読んでいない](https://zenn.dev/zhizhiarv/articles/claude-code-webfetch-haiku-summary)

**ひとこと**  
WebFetch は「取ってきたサイズ」と「実際に上位モデルへ渡った内容」が一致しないことがある、という話でした。

**読んで考えたこと**  
記事では、Claude Code の WebFetch が多くの場面で原文をそのまま読まず、いったん小さなモデルで要約・抽出した結果を上位モデルに渡していると整理していました。`Received 204.4KB` と表示されても、実際には全文相当を読めていないことがある、というのはかなり重要です。

気になったのは、これが単なる「要約される」ではなく、複数段階で truncation が入ることでした。

- HTTP 取得上限がある
- HTML は先頭 1MiB だけ処理される
- Haiku に渡す前に 10 万文字で切られることがある

この構造だと、長文の後半が静かに落ちても、利用者側からは気づきにくいです。実装や調査で一次情報を見ているつもりでも、実際は要約の要約を読んでいるだけ、という状態になりやすいと思いました。

一方で、信頼ドメインかつ Markdown 対応、かつ一定長以下なら要約をバイパスできるケースもあるので、常に同じ挙動ではないです。そこがまたややこしいです。  
運用上は、WebFetch の結果をそのまま信用せず、必要なら `curl` や `defuddle parse URL --md`、専用 MCP ツールで原文を取りにいく方が安全そうでした。

## Codex は SDK と App Server で役割がかなり違う

**元記事**  
[「Codex App Server」を試す](https://zenn.dev/kun432/scraps/9fe862943fb00e)

**ひとこと**  
Codex は「自動化用」と「UI 統合用」で入口を分けて考えると分かりやすい、という整理でした。

**読んで考えたこと**  
この記事は、Codex SDK と Codex App Server の違いをかなり丁寧に整理していました。読んでいて一番助かったのは、用途で役割が分かれていることです。

- **Codex SDK**  
  CI/CD、社内ツール、ジョブ自動化向け
- **Codex App Server**  
  IDE や独自 UI を作るとき向け
- **codex exec / GitHub Action**  
  単発実行や CI 向け
- **Codex App / IDE Extension / Web**  
  人間が普段触る完成 UI 向け

App Server の話で印象に残ったのは、単なる API ではなく、認証・会話履歴・承認・リアルタイムイベントまで含めた「クライアントを作るための土台」だという点でした。Item / Turn / Thread で状態を表すので、UI 側はストリーミングや承認ダイアログを組み込みやすそうです。

ただ、そのぶん低水準で、JSON-RPC 処理や状態管理、イベント表示、承認 UI は自前実装になります。ここは軽く試すより、ちゃんと製品に入れる前提で設計しないと重いです。  
個人用途で ChatGPT サブスクを活かした自作 UI を作る、という文脈ではかなり面白いですが、記事でも触れられていた通り、パブリック公開アプリのバックエンドで雑に使う話ではなさそうでした。認証、権限、セッション管理の負担が増えるので、そこは慎重に見た方がよさそうです。

## 今週の所感

AI エージェントは「賢いかどうか」より、「何を本当に読んでいて、どこで要約や抽象化が入るか」を先に確認した方が安全だと思いました。WebFetch も Codex も、便利さの裏で境界がはっきりあるので、次に試すならまずその境界の確認からやりたいです。
