## WebFetch の中で起きていること

**元記事**  
[あなたのClaude CodeのWebFetch、実はWebをちゃんと読んでいない](https://zenn.dev/zhizhiarv/articles/claude-code-webfetch-haiku-summary)

**ひとこと**  
Claude Code の WebFetch は、原文をそのまま読んでいるつもりでも、実際には小さいモデルの要約を経由していることが多い、という指摘でした。

**読んで考えたこと**  
ここで一番気になったのは、「Fetched したサイズ」と「実際にモデルへ渡った内容」が一致しないことです。画面上は大きなページを取ってきたように見えても、後段では要約だけになっているので、ユーザー側からは判別しにくいです。

実装上も複数の切り捨てが入っていて、

- HTML は先頭 1MiB だけ処理
- Markdown は 10 万文字超で切り捨て
- 信頼ドメインかつ `text/markdown` かつ 10 万文字未満なら要約をバイパス

という条件があるので、「全文を読んだ前提」で議論するのは危ないと思いました。

運用するなら、こういう場面では WebFetch を信用し切らず、

- 原文が必要なら `curl` や `defuddle` で取りにいく
- ドキュメント系は専用 MCP や公式ツールを優先する
- 重要な仕様確認は要約ではなく一次情報を確認する

という分け方が必要そうです。AI に AI の要約を読ませると、伝言ゲームで精度が落ちる、という感覚はかなり実感に近いです。

## Codex を自作アプリにどう入れるか

**元記事**  
[「Codex App Server」を試す](https://zenn.dev/kun432/scraps/9fe862943fb00e)

**ひとこと**  
Codex を使う方法がいくつかある中で、App Server は「UI を作るための層」、SDK は「自動化するための層」と分けて考えると分かりやすい、という整理でした。

**読んで考えたこと**  
この記事で助かったのは、Codex App Server を「なんでもできる便利機能」として見るのではなく、用途がかなり限定された部品として整理している点です。特に、認証・会話履歴・承認・ストリーミングを含むリッチなクライアントを作るなら App Server、CI/CD や社内ジョブに載せるなら SDK や `codex exec`、という線引きは実務で判断しやすいです。

運用目線だと、App Server はかなり強い一方で、

- JSON-RPC over stdio 前提でクライアント実装の負担がある
- 状態管理やイベント処理を自前で持つ必要がある
- 公開アプリのバックエンドで使う設計は認証や課金の面で慎重さが必要

という重さがあります。

逆に、個人用途や社内用途なら、ChatGPT サブスクの範囲を活かして「自分のアプリから Codex を呼ぶ」設計はかなり現実的に見えました。ここは無料 API 枠で遊ぶのとは違って、Codex のハーネスそのものを使えるのが大きいです。自前で LLM UI を全部作るより、認証や承認の流れを寄せられるのは運用コストを下げられそうでした。
