今週は、AIエージェントの「読んだつもり」「使えるつもり」を少し疑いたくなる話が2本並んでいました。どちらも、機能そのものより「実際に何が起きているか」を見ないと運用を誤りやすい、という点が印象に残りました。

## Claude Code の WebFetch はどこまで読んでいるのか

**元記事**  
[あなたのClaude CodeのWebFetch、実はWebをちゃんと読んでいない](https://zenn.dev/zhizhiarv/articles/claude-code-webfetch-haiku-summary)

**ひとこと**  
WebFetch で「読めた」と思っていても、実際は要約しか見ていない場面がある、という指摘がかなり重かったです。

**読んで考えたこと**  
記事の主張は、Claude Code の WebFetch が多くの場合、原文をそのままメインモデルに渡していないという点でした。まず小型モデルで要約・抽出して、その結果を上位モデルが読む構造になっていて、長文では後半が静かに落ちることもあるようです。

運用面で気になったのは、`Received 204.4KB` のように見えても、実際には全文ではなく要約しか届いていないケースがあることです。表示と実態がずれるので、ドキュメント確認や仕様調査をそのまま任せるのは危ないと思いました。

実装で見ると、長文HTMLの前処理、先頭部分の切り出し、要約、信頼ドメインだけのバイパスなど、段階ごとに情報が削られる設計でした。コストやPrompt Injection対策としては納得できますが、ユーザー側からは見えにくいです。  
一次情報が必要な場面では、WebFetch任せにせず、`curl` や `defuddle parse URL --md`、あるいは専用MCPで原文を取りにいく運用のほうが安心だと感じました。

## Codex App Server は「UIを作るためのハーネス」だった

**元記事**  
[「Codex App Server」を試す](https://zenn.dev/kun432/scraps/9fe862943fb00e)

**ひとこと**  
Codex を単体のアプリではなく、クライアントから再利用する基盤として見ると整理しやすい記事でした。

**読んで考えたこと**  
この記事は、Codex の使い方を `Codex App Server`、`Codex SDK`、`codex exec`、GitHub Action、App/IDE拡張に分けて整理していました。中心にあるのは、会話履歴、承認、イベントストリーミング、認証まで含む「ハーネス」をどう使うか、という見方です。

特に App Server は、リッチクライアントを作るための低水準な接続口という位置づけでした。JSON-RPC over stdio で、UI側が状態管理や承認フローをかなり持つ必要があるので、雑に使えるものではないです。その代わり、承認付きのAI操作や差分のリアルタイム表示を既存ツールに組み込みたい時には、かなり相性がよさそうです。

一方で、自動化やCI/CDなら SDK や `codex exec` のほうが自然でした。App Server は UI 統合向け、SDK はバックエンドやジョブ向け、という線引きがわかりやすいです。  
個人用途であれば、ChatGPT のサブスクを活かして自分専用の Codex クライアントを作る、という発想が取りやすいのも面白かったです。ただし、公開アプリや商用バックエンドで同じ使い方ができるかは別問題なので、その辺は公式仕様を改めて確認したくなりました。

## 今週の所感

AIツールは「便利に見える入口」と「実際に読んでいる中身」がズレやすいので、原文確認が必要な場面を自分で決めておくのが大事そうです。WebFetch も Codex も、どこで要約や抽象化が入るかを把握しておくと、あとから悩む回数が減りそうだと思いました。
