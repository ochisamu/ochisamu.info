今週は、AI エージェントの「安全な実行基盤」と「安全に公開する仕組み」が印象に残りました。どちらも、LLM の賢さそのものより、その周囲をどう隔離し、どう運用に落とすかが勝負になっている話でした。

## Clip 23
### 元記事
[AIエージェントを安全に動かすための技術——サンドボックスについて調べてみる](https://zenn.dev/layerx/articles/a99cd11af487fc)

### ひとこと
AI エージェントを提供するなら、まず Sandbox をどう切るかが本丸だと思う。メガクラウドが標準で従量提供してくれたらかなり助かる、という感覚もよく分かる。

### 読んで考えたこと
記事は、AI エージェントがコード実行・ブラウザ操作・外部 API 叩きまでやる前提では、通常のアプリより隔離の重要性が一段上がる、という整理が中心でした。  
隔離方式も、プロセス分離、gVisor、VM 分離、WASM と並べて、強度と互換性のトレードオフとして見ているのが分かりやすいです。

特に印象的だったのは、強い隔離が必要なマネージド環境では gVisor か microVM 系が選ばれやすい、という実務寄りの観察でした。  
「Sandbox があれば安全」という単純な話ではなく、どこまでをホストと切り離せるか、どこで互換性を捨てるか、という設計判断の話なんだと再確認しました。

## Clip 20
### 元記事
[非エンジニアの「作りたい」と「安全に公開したい」を両立する Sandbox MCP を作った](https://zenn.dev/aircloset/articles/65efe9614f8e73)

### ひとこと
「作れる」と「公開できる」の間にある面倒を、プラットフォーム側で全部肩代わりする発想が面白い。AI 活用の次のボトルネックは、まさにそこだと感じる。

### 読んで考えたこと
記事は、非エンジニアが Claude Code などで作った社内アプリを、統一された UI と認証、DB 分離、ドメイン、デプロイまで含めて安全に公開するための Sandbox MCP の紹介でした。  
単なる開発補助ではなく、公開までの責務をプラットフォーム化しているのがポイントです。

また、大きめのアプリでは MCP 経由のファイル転送だけだとトークン消費やサイズ制限が厳しくなるので、git push を併用している、という運用上の工夫も実践的でした。  
AI がコードを書くようになったからこそ、作る人に全部任せず、公開・分離・認証・運用の“標準”を用意する必要がある、という主張として読むと納得感があります。

## 今週の所感
2 本を並べて読むと、AI エージェントや AI 生成アプリの課題は、モデル性能よりも周辺基盤に寄ってきていると感じました。  
1 本目は「未信頼な実行をどう隔離するか」、2 本目は「作ったものをどう安全に公開するか」。どちらも、便利さを本番で使える形にするには、サンドボックスとプラットフォーム設計が欠かせない、という話でした。
